# 子模块详细设计文档模板

## 文档头部（表格，非 blockquote）

```markdown
# 子模块：<名称>（<简述>）

| 属性 | 值 |
|---|---|
| 创建 | YYYY-MM-DD（来源说明） |
| 修改 | YYYY-MM-DD（变更摘要，简短） |
| 阶段 | P1 xxx / P2 xxx / P3 xxx |
| 前置 | xxx / xxx |
```

---

## §1 需求背景与目标

- **背景**：2-3 句话说明当前现状、存在的痛点、为什么需要这个模块
- **目标**：表格式 `| # | 目标 | 验收 | 阶段 |`，每个目标可验证、可度量

## §2 需求边界

- 开头一句话总结模块定位
- **关键概念定义**：如有核心术语，在此明确定义
- **做什么**：按端（如 SDK 端 / 服务端）分表，每行 `| 组件名 | 职责 |`
- **不做什么**：表格式 `| 事项 | 归属 |`
- 未实现的组件标注 `**P3+ 暂不实现**`，待实现的标注 `（待实现）`

## §3 UseCase

- 按场景分组，每组一张部署图 + 一张行为表
- 部署图使用 `flowchart`，边标签用短文本（1-3 词）
- 每张图下方表格按操作类型区分行为
- 末尾一张 UseCase 总表：6 列（UseCase | 使用者 | 场景 | 需要什么 | 设计响应 | 验收）

> **UseCase 抽象层级规则**：UseCase 从**外部视角**描述使用者与本模块的交互。
> 图中参与者只画"使用者"和"本模块"（黑盒），**不画本模块的内部组件**（如子类、filter、manager 等）。
> 内部组件的交互、数据流、状态变更属于 §4 方案设计的内容，不在 UseCase 中展开。
> UseCase 只回答：使用者调什么接口、模块返回什么、异常时双方怎么协作。

## §4 方案设计

- **4.1 类图**：只列对外 API（public 方法），组合关系用 `*--`，产出用 `..>`
- **4.2 开发视图**：文件树，标注每个文件的职责
- **4.3 关键交互**：每个关键场景一个时序图。错误码映射用表。代码骨架只保留核心逻辑
- **4.4 模块依赖图**：用 `flowchart` 展示模块间调用/依赖关系
- **4.5 关键数据结构**：每个结构独立一小节。复用既有类的注明来源。并发安全说明（锁/无锁/RCU）
- **4.6 组件接口设计**：模块内部组件间的接口协议。总览表 + 每个接口的信号格式/数据载体

## §5 对外接口

- **5.1 SDK 接口**：`| 接口 | 调用方 | 频率 | 说明 |`
- **5.2 部署参数**：`| 参数名 | 类型 | 默认值 | 说明 |`
- **5.3 环境变量**：`| 变量 | 默认值 | 说明 |`

## §6 约束 + 风险

- **约束**：`| # | 约束 | 违规后果 |`，只列"违反会出问题"的真正约束
- **风险**：`| # | 风险 | 缓解 |`

## §7 落地步骤

- 按端分表（如 SDK 端 / 服务端），列：PR 编号 | 内容 | 阶段

## §8 测试方案

- **UT**：`| 文件 | 覆盖点 | 覆盖率 |`
- **IT**：每行对应一个 UseCase，`| IT | 对应 UseCase | 场景 | 断言 |`
